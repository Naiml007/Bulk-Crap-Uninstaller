# Win11 theme tokens, DWM title bar / Mica, and owner-drawn control set

This change adds a Windows 11 visual layer to Bulk Crap Uninstaller: a static token class (`Win11Theme`) that owns all colors, a DWM helper that sets the dark title bar and Mica backdrop, and three owner-drawn controls (`Win11Button`, `Win11TextBox`, `Win11CheckBox`) substituted into five Designer.cs files. The motivation is to make the app feel native on Win11 22H2+ while degrading gracefully on older builds. The approach is standalone — no new NuGet dependencies, pure GDI+ rendering, tokens read at paint time so light/dark is automatic without re-instantiation.

**Watch for:** (confirmed) `Win11TextBox` sets `BackColor`/`ForeColor` once in the constructor and never re-applies them when `ThemeChanged` fires, so its colors are frozen at startup. (confirmed) `SettingsWindow` and all secondary windows never call `ApplyTheme`, so their title bars do not get dark mode styling. (confirmed) Several `CheckBox` controls in `SettingsWindow` were left as the standard type — the substitution is partial and inconsistent within the same form.

**Verdict**: NEEDS_CHANGES

---

## High-level view

`Win11Theme` is a static color-token bag with a `ThemeChanged` event wired to `SystemEvents.UserPreferenceChanged`. Colors are computed as properties reading `IsDarkMode` at call time, so a repaint after a theme switch automatically picks up the right values — this is the strongest part of the design.

`Win11DwmHelper` calls `DwmSetWindowAttribute` twice: once for the dark title bar (always attempted), and once for Mica (gated on build ≥ 22621). Both calls are wrapped in independent try/catch blocks, so a failure on older Windows is silent.

The DWM theme is only applied in `MainWindow`. The four other windows that received Win11 controls (`SettingsWindow`, `UninstallProgressWindow`, `JunkRemoveWindow`, `BeginUninstallTaskWizard`) have Win11-styled buttons and checkboxes but standard title bars regardless of dark mode state.

`Win11TextBox` captures `BackColor` and `ForeColor` from theme tokens at construction time. When the user switches between light and dark mode, the text field backgrounds and text colors do not update — only the border paint in `WndProc` does. This is inconsistent with how `Win11Button` and `Win11CheckBox` behave (they read tokens on every paint).

The substitution in `SettingsWindow.Designer.cs` is partial: `checkBoxEnableExternal`, `checkBoxRemovable`, `checkBoxAutoInstallFolderDetect`, `checkBoxScanSteam`, `checkBoxScoop`, `checkBoxOculus`, `checkBoxChoco`, `checkBoxScanWinFeatures`, `checkBoxScanStoreApps` all remain as standard `CheckBox`. On the same settings tab, mixed styled and unstyled checkboxes will appear side by side.

<summary>Issues (5)</summary>

1. **Win11TextBox ignores ThemeChanged** — `BackColor` and `ForeColor` are set once in the constructor from `Win11Theme` tokens. After a light→dark switch, the text field retains its light background while buttons and checkboxes repaint correctly. Fix: override `OnBackColorChanged` or subscribe to `Win11Theme.ThemeChanged` in the control and call `BackColor = Win11Theme.FillSolidBase; ForeColor = Win11Theme.TextPrimary; Invalidate();`.

2. **Secondary windows missing ApplyTheme** — `SettingsWindow`, `UninstallProgressWindow`, `JunkRemoveWindow`, and `BeginUninstallTaskWizard` get Win11 controls but no DWM title-bar styling. On dark mode they will have owner-drawn dark buttons inside a light title bar. Fix: call `Win11DwmHelper.ApplyTheme(this)` in each form's constructor and subscribe to `Win11Theme.ThemeChanged` the same way `MainWindow` does.

3. **Partial checkbox substitution in SettingsWindow** — The Detection tab retains eight standard `CheckBox` controls (`checkBoxEnableExternal`, `checkBoxRemovable`, `checkBoxAutoInstallFolderDetect`, `checkBoxScanSteam`, `checkBoxScoop`, `checkBoxOculus`, `checkBoxChoco`, `checkBoxScanWinFeatures`, `checkBoxScanStoreApps`). These will render with the system default glyph next to Win11-styled checkboxes. Fix: substitute the remaining controls, following the same pattern already applied in the diff.

4. **ThemeChanged subscription is never removed** — The lambda in `MainWindow` captures `this` and is added to a static event, which prevents GC of `MainWindow` as long as `Win11Theme`'s static instance lives. For a single-window app this is usually harmless, but the subscription should be removed in `MainWindow`'s `Dispose` or `FormClosed` handler to avoid a dangling reference if the form is ever re-created.

5. **Win11CheckBox uses a newly allocated Font per paint** — The `using var checkFont = new Font("Segoe UI", 8f, ...)` inside `OnPaint` allocates and immediately disposes a GDI font object on every redraw. The equivalent of `Win11Theme.BodyFont` already exists on the class. Fix: use `Win11Theme.BodyFont` for the checkmark glyph (or cache a static font field in `Win11CheckBox`) to avoid GDI churn during list repaints.

<details>
<summary>Details</summary>

### Theme token design and dark-mode detection

Color properties compute from `IsDarkMode` at the call site, so any control that reads tokens during `OnPaint` gets the correct value without needing to subscribe to `ThemeChanged`. `Win11Button` and `Win11CheckBox` do this correctly. `Win11TextBox` does not — it caches the values in WinForms properties at construction time.

### DWM integration scope gap

None of the four secondary forms call `ApplyTheme`. A user who opens Settings in dark mode will see a dark-accented button set in a light-chrome window.

### Partial control substitution in SettingsWindow

The diff substitutes 11 out of 19 `CheckBox` controls in `SettingsWindow`. The ones remaining on the Detection tab are skipped — per the FEAT-004 findings note, `textBoxProgramFolders` was also intentionally left, but the Detection tab checkboxes have no such note. The result is a mixed appearance within a single window.

### Win11TextBox border painting approach

`Win11TextBox` hooks `WndProc` to intercept `WM_PAINT` (0x000F) and `WM_NCPAINT` (0x0085) and draws the border with `CreateGraphics()` after `base.WndProc`. The focus ring (2px accent bottom line) correctly checks `_hasFocus` set via `OnGotFocus`/`OnLostFocus`. What is missing is a `BackColor`/`ForeColor` refresh on theme change — the colors set in the constructor stay fixed for the lifetime of the control.

### ThemeChanged event leak and GDI font allocation

The lambda `(s, e) => { Win11DwmHelper.ApplyTheme(this); Invalidate(); }` captures `this` (the `MainWindow` instance) and is registered against `Win11Theme.ThemeChanged`, a static event. Static event subscriptions hold strong references to the delegate, which holds a strong reference to the captured `this`. Since `MainWindow` is effectively a singleton in this application this will not cause a practical memory leak, but it is a correctness issue if the form is ever disposed and re-created.

Inside `Win11CheckBox.OnPaint`, a `Font` object is allocated on every call: `new Font("Segoe UI", 8f, FontStyle.Regular, GraphicsUnit.Point)`. GDI font handles are limited system resources. For a list view with many checkboxes visible, rapid repaints will generate high GDI churn. `Win11Theme.BodyFont` is already a cached static property; reusing it eliminates the allocation.
