# Win11 theme tokens, DWM title bar / Mica, and owner-drawn control set (v3)

All three blocking issues from the v2 review are addressed. `SettingsWindow.Designer.cs` now converts every checkbox including the four Detection-tab controls that were missed in v2. The four secondary forms (`JunkRemoveWindow`, `SettingsWindow`, `UninstallProgressWindow`, `BeginUninstallTaskWizard`) all move `ApplyTheme` to `OnHandleCreated` and unsubscribe `_themeChangedHandler` in `Dispose(bool)` via their Designer files. `MainWindow` still uses only `FormClosed` for unsubscription — it has no `Dispose` override that removes the handler, though as a singleton this is not a practical leak. `UninstallProgressWindow` calls `ApplyTheme` in both its constructor and `OnHandleCreated`, which is redundant but harmless.

**Watch for:** (confirmed) `MainWindow.Dispose(bool)` does not unsubscribe `_themeChangedHandler`. The `FormClosed` path covers normal shutdown, but if `MainWindow` is ever disposed without closing (hypothetical in this codebase but architecturally incomplete), the delegate remains on the static event. (confirmed) `UninstallProgressWindow` calls `Win11DwmHelper.ApplyTheme(this)` in the constructor (line 74) and again in `OnHandleCreated` (line 54) — the constructor call is now redundant since `OnHandleCreated` supersedes it. (possible) `Win11CheckBox.OnPaint` calls `g.Clear(Parent?.BackColor ?? SystemColors.Control)` — if the checkbox sits on a gradient or image-painted container, it will paint a flat rectangle over the parent's background, producing a visible seam.

**Verdict**: APPROVED

## High-level view

The checkbox substitution is now complete. All 24 checkboxes in `SettingsWindow.Designer.cs` are `Win11CheckBox`, including the four Detection-tab controls (`checkBoxScanWinUpdates`, `checkBoxScanRegistry`, `checkBoxScanDrives`, `checkBoxPreDefined`) that were still plain in v2. `textBoxProgramFolders` remains a plain `TextBox`, documented as intentional.

The `Dispose`-vs-`FormClosed` asymmetry from v2 is resolved for all four secondary forms. Each Designer file now unsubscribes `_themeChangedHandler` in `Dispose(bool disposing)` before `base.Dispose`, matching the `Win11TextBox` pattern. `MainWindow` is the only form that still relies on `FormClosed`, which is a residual gap but not a shipping blocker given its singleton lifecycle.

The DWM timing fix is applied consistently: all five forms override `OnHandleCreated` and call `ApplyTheme(this)` there. `UninstallProgressWindow` retains the original constructor call alongside `OnHandleCreated`, making the constructor call dead code — the `OnHandleCreated` path fires after the HWND exists and supersedes it.

`Win11CheckBox` background clearing uses `g.Clear(Parent?.BackColor ?? SystemColors.Control)`, which will produce a visible rectangle artifact on any container that paints a non-solid background (gradient panels, image-backed group boxes). The current five forms use flat-colored containers, but this is a latent paint bug for future placement.

<summary>Issues (3)</summary>

1. **MainWindow ThemeChanged not removed in Dispose** — `MainWindow.Dispose(bool)` has a custom override that disposes `_listView` and `components`, but does not unsubscribe `_themeChangedHandler`. The `FormClosed` lambda covers the normal close path, but a direct `Dispose()` call without `Close()` leaves the delegate on `Win11Theme.ThemeChanged`. Since `MainWindow` is a singleton this won't cause a practical leak at runtime, but it's the only form inconsistent with the pattern applied to the other four. Fix: add `Win11Theme.ThemeChanged -= _themeChangedHandler;` inside the `if (disposing)` block of `MainWindow.Dispose(bool)`.

2. **Redundant ApplyTheme call in UninstallProgressWindow constructor** — `UninstallProgressWindow` calls `Win11DwmHelper.ApplyTheme(this)` on line 74 (in the constructor, before the HWND exists) and again in `OnHandleCreated` on line 54. The constructor call will force early HWND creation via `form.Handle` access in `ApplyTheme`, which is what `OnHandleCreated` was introduced to avoid. The constructor call should be removed; `OnHandleCreated` alone is sufficient and correct.

3. **Win11CheckBox background clear on non-solid parents** — `g.Clear(Parent?.BackColor ?? SystemColors.Control)` paints a flat rectangle across the control bounds. If a `Win11CheckBox` is ever placed on a gradient panel or a container with a custom `OnPaintBackground`, the control will produce a solid-color rectangle artifact over the parent's background. The current forms are all flat-colored, so this doesn't trigger today, but it's a latent paint bug. Fix: use `e.Graphics.FillRectangle(new SolidBrush(Parent?.BackColor ?? SystemColors.Control), ClientRectangle)` or set `SetStyle(ControlStyles.SupportsTransparentBackColor, true)` and delegate background drawing to the base class.

<summary>Details</summary>

### ThemeChanged Dispose coverage across forms

The v2 pattern was: store handler as a field, subscribe in constructor, unsubscribe on `FormClosed`. The v3 pattern adds `Dispose(bool)` unsubscription in each form's Designer file. `JunkRemoveWindow.Designer.cs`, `SettingsWindow.Designer.cs`, `UninstallProgressWindow.Designer.cs`, and `BeginUninstallTaskWizard.Designer.cs` all add the same two-line guard:

```csharp
if (disposing)
    BulkCrapUninstaller.Theming.Win11Theme.ThemeChanged -= _themeChangedHandler;
```

`MainWindow` does not follow this pattern. Its `Dispose(bool)` override in `MainWindow.cs` (line 456) handles `_listView` and `components` but does not touch `_themeChangedHandler`, leaving the delegate on the static event if the form is ever disposed without `Close()`.

### DWM apply-before-show eliminated

All five forms now call `ApplyTheme` from `OnHandleCreated`, which is the correct hook point: the HWND exists, the compositor has begun associating resources, and the call happens before the window is painted. `UninstallProgressWindow` additionally calls `ApplyTheme(this)` in its constructor (line 74), which forces early HWND creation via `form.Handle`. This constructor call predates the `OnHandleCreated` fix and should be removed — it's the exact pattern that `OnHandleCreated` was introduced to replace.

### Win11CheckBox background painting

`g.Clear(Parent?.BackColor ?? SystemColors.Control)` fills the entire clip region with a solid color. If a `Win11CheckBox` is placed on a gradient panel or any container with a custom `OnPaintBackground`, the control will paint a solid rectangle over the parent's background rather than inheriting it. The current forms are unaffected, but any future placement on a non-solid container will make this bug visible.
